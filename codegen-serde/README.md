# Configurable serde code generation

`codegen-serde` adds configurable [serde](https://serde.rs/) serialization and
deserialization to types generated by smithy-rs clients and servers.

This support is intended for convenience use cases such as logging, snapshots,
and application-owned data interchange. It is separate from Smithy protocol
serialization: the serde representation is not guaranteed to match any Smithy
wire protocol.

## Enable serde for model shapes

Put `codegen-serde` on the code generator classpath, then apply the
`smithy.rust#serde` trait to the shapes that need serde support:

```smithy
$version: "2"

namespace example

use smithy.rust#serde

@serde(serialize: true, deserialize: true)
structure AuditRecord {
    message: String
    ratio: Float
}
```

The trait has two settings:

| Setting | Default | Effect |
| --- | --- | --- |
| `serialize` | `true` | Generates configurable `serde::Serialize` support. |
| `deserialize` | `false` | Implements `serde::Deserialize` for the generated type. |

`@serde` may also be applied to a service or operation to enable serde for its
supported input and output shapes. If no annotated root enables either
direction, the generated crate has no serde feature or support.

Generated crates expose this support behind an optional `serde` Cargo feature.
Enable it on the generated crate:

```toml
[dependencies]
my-generated-crate = { path = "../generated", features = ["serde"] }
serde = { version = "1", features = ["derive"] }
serde_json = "1"
```

## Serialize generated types

Serialization uses `SerializeConfigured`, which returns a serde-compatible
wrapper around the generated type. The examples use the client module layout;
import server types from their corresponding generated modules.

```rust
use my_generated_crate::serde::{
    SerializationSettings,
    SerializeConfigured,
};
use my_generated_crate::types::AuditRecord;

fn to_json(record: &AuditRecord) -> serde_json::Result<String> {
    let mut settings = SerializationSettings::default();
    settings.out_of_range_floats_as_strings = true;

    serde_json::to_string(&record.serialize_ref(&settings))
}
```

Use `serialize_owned` instead when the serializer wrapper must own the value:

```rust
let serializable = record.serialize_owned(settings);
let json = serde_json::to_string(&serializable)?;
```

`SerializationSettings` currently provides:

- `redact_sensitive_fields`: replaces values targeted by `@sensitive` with
  `"<redacted>"`. Redaction can change the serialized type and may make the
  output impossible to deserialize into the original model type.
- `out_of_range_floats_as_strings`: writes `NaN`, `Infinity`, and
  `-Infinity` as strings instead of relying on the format's non-finite float
  behavior.

The generated module also exports `serialize_redacted` and
`serialize_unredacted` for embedding generated types in application-owned
types:

```rust
use my_generated_crate::serde::serialize_redacted;
use my_generated_crate::types::AuditRecord;
use serde::Serialize;

#[derive(Serialize)]
struct Event {
    #[serde(serialize_with = "serialize_redacted")]
    record: AuditRecord,
}
```

## Deserialize generated types

Shapes with `deserialize: true` implement `serde::Deserialize` directly:

```rust
use my_generated_crate::types::AuditRecord;

let record: AuditRecord =
    serde_json::from_str(r#"{"message":"ready","ratio":1.5}"#)?;
```

Deserialization settings are applied through a synchronous, thread-local
scope:

```rust
use my_generated_crate::serde::DeserializationSettings;
use my_generated_crate::types::AuditRecord;

let mut settings = DeserializationSettings::default();
settings.allow_non_finite_float_strings = true;

let record = settings.scope(|| {
    serde_json::from_str::<AuditRecord>(
        r#"{"message":"ready","ratio":"Infinity"}"#,
    )
})?;
```

`allow_non_finite_float_strings` accepts `NaN`, `Infinity`, and `-Infinity`
strings for floating-point fields. It is disabled by default.

Scopes may be nested and restore the previous settings after returning or
panicking. Settings do not cross threads. The scope is synchronous: returning
a future from the closure does not keep the settings active while that future
is polled.

## Format considerations

Generated implementations use serde's data model and work with serializers and
deserializers such as `serde_json` and `ciborium`. They do not reproduce Smithy
protocol bindings, timestamp formats, headers, payload placement, or error
envelopes.

Unset optional structure members are currently omitted during serialization.
The generated serializer still reports the modeled member count to serde.
Formats that rely on an exact, up-front structure length may therefore reject
or misread structures with unset optional members. JSON is not affected;
length-sensitive formats such as CBOR should only be used when the selected
serializer can handle this representation or all serialized members are
present.

Non-self-describing formats also require the serializer and deserializer to
agree on the same shape and field order. Test the exact model and format
combination used by the application.
