C02: whitespace in plain string prefix-header values
Validated 2026-10-14 against freshly generated legacy and schema servers.

Source evidence
  HttpBindingGenerator.generateDeserializePrefixHeaderFn uses
  HttpHeaderValueParserGenerator.renderHeaderValueParser for map values.
  Plain strings (including enums) use one_or_none_bytes, whose implementation
  in aws-smithy-runtime-api/src/http/header_parse.rs calls str::trim.
  Schema RestRequestDeserializer previously passed the raw UTF-8 value into
  StringMapDeserializer without trimming it.

Observable discrepancy
  An x-meta-key header containing "  red  " reached the legacy handler as "red"
  but reached the schema handler with the spaces intact. Unicode whitespace
  behaved similarly. With an enum map value, " red " passed legacy validation
  but schema returned 400 instead of invoking the handler.

Fix
  Trim borrowed plain string prefix-header values at the binding step. This
  includes enum values and uses the same str::trim semantics as legacy.
  The shared query-map reader is unchanged. Quotes, commas and interior spaces
  remain intact. The change introduces no extra string allocations.

Test contract
  Generate fresh REST JSON and REST XML servers with schemaSerde=false, then
  schemaSerde=true, using HTTP 1.x. Legacy must first pass 26 explicit controls
  per protocol. Successful handlers echo their parsed input in a string payload.
  Compare status, all response headers and exact body bytes for every request.
  Logging and media-type decoding remain separate audit items.

Coverage
  Spaces, tabs, Unicode whitespace, Unicode text, zero-width spaces, empty and
  absent values, interior whitespace, quotes and commas, mixed-case names,
  multiple map entries, an empty suffix, duplicates, invalid UTF-8, and enums.
  Each ordinary-string success also verifies that direct headers still trim,
  while scalar queries and query-map values retain their whitespace.
