# A/B fuzzing: single-protocol servers versus one multi-protocol server

Sends the same fuzzed HTTP request to a generated serde single-protocol server generated by `$BASELINE_REPO`
and to a schema server generated by this checkout, and saves the request
when the two answer differently. Background: [AB_FUZZING.md](AB_FUZZING.md) (the general runbook) and
[how-to-benchmark.md](../../how-to-benchmark.md) (the same baseline/current setup, for performance).

Run the scripts with `bash` from this directory. Everything they produce goes under `artifacts/`, which
Git ignores.

```bash
export BASELINE_REPO=/path/to/clean/legacy/smithy-rs
bash fuzz.sh 900 2         # check, generate, initialize, fuzz for 15 minutes, then replay
python3 abfuzz.py cluster multiprotocol rest-json1 -v 3    # samples of each group
```

Prerequisites: Git, Java and the repository's Gradle build dependencies, Rust/Cargo
and rustup, Python 3, GNU `timeout`, and `cargo-afl` matching the `afl` version in
`rust-runtime/aws-smithy-fuzz/Cargo.lock`. `fuzz.sh` checks the required commands,
checkout layout, and clean baseline before generation. It does not install missing
tools or update the baseline.

Every default invocation regenerates the SDKs and rebuilds targets, then compares
the initial seeds. Generation, build, or seed differences stop the run before AFL
starts. The duration excludes setup time. Existing saved crashes and hangs are
preserved unless `FRESH=1` is explicitly set.

For one case:

```bash
SUITES=pokemon CASES=rest-json1 bash fuzz.sh 900 2
```

Individual stages remain available as `generate.sh`, `init.sh`, and `replay.sh`.
If generation and initialization have already passed for the current sources,
`bash fuzz.sh --prepared 900 2` runs fuzzing and replay without repeating them.
`campaign.sh` uses this mode for its explicitly prepared protocol variants.

Source `env.sh` first when running `abfuzz.py` or `aws-smithy-fuzz` by hand.

## What is compared

| | Checkout | Server |
| --- | --- | --- |
| `single` | `$BASELINE_REPO` (required explicit path) | one generated serde server per protocol |
| `multi` | this checkout | isolated `schemaSerde` server per protocol by default; combined profiles are explicit |

Two suites (`SUITES`): `multiprotocol` reads its models and server fixtures from
`codegen-core/common-test-models/multi-protocol-compat`; `pokemon` reads its
shared models from `codegen-core/common-test-models` of this checkout.
Five cases (`CASES`) per suite cover the five protocols. Set `MP_FUZZ_ISOLATE_PROTOCOLS=false`
explicitly to generate combined protocol variants.
Combined routing differences remain failures.

The baseline must be pristine; the current checkout may include local changes.
`CURRENT_REPO` defaults to the checkout containing these scripts. Set `FUZZ_ROOT`
to override the output directory.
`artifacts/gen/revisions.txt` records their state. Nothing in the baseline source tree is modified: the generator test
(`fuzzgen/.../MultiProtocolAbFuzzHarnessTest.kt`) is compiled into its `fuzzgen` tests through
`fuzzgen-extra-tests.init.gradle`. Both fuzz targets of a case are generated by this checkout's `fuzzgen`,
so both implement the same operations; the `single` target links the baseline's runtime.

Event-stream operations are included. Handlers drain incoming events, preserve modeled error details,
and emit a deterministic example of each output event and modeled exception. Plain blob streaming
operations remain excluded.

Generated serde AWS JSON codegen rejects event-stream inputs with additional input members. For profiles serving
AWS JSON, `Publish.topic` and `CapturePokemon.region` are explicitly removed, and the capture route becomes
`/capture-pokemon-event`. CBOR-only and REST-only profiles retain these members and the region route. The generated
harness integration tests separately cover initial-request frames on the schema path.

Greet retains HTTP 201; status differences fail comparison.

### Canonical model versus fuzz model

The generic A/B target does **not** cover the entire canonical model. Explicit Smithy shape transforms
currently exclude these case families on both sides:

| Canonical element | Reason | Scope |
| --- | --- | --- |
| Upload | Generic handler lacks plain streaming blob input | All generic profiles; independently tested on REST |
| StreamPokemonRadio | Generic handler lacks plain streaming blob output | All generic profiles; runtime coverage remains a gap |
| PublishInput$topic | Generated serde AWS JSON requires an event stream to be the sole input member | Both sides of AWS JSON-serving profiles only |
| CapturePokemonInput$region | Same AWS JSON restriction | AWS JSON-serving profiles; capture route explicitly loses the region label |

These restrictions do not make the canonical Smithy models invalid. REST supports plain blob streams
and additional bound members. Current-tree generated serde CBOR generates original Publish.topic successfully;
it is not a blanket RPC generation restriction. CBOR and REST retain these members whenever their
profile does not also serve AWS JSON. Upload and StreamPokemonRadio remain explicit generic-handler
limits; their omission is not required by REST codegen.

Each side/profile writes `model-projection.json`, `canonical-model.json`, and `fuzz-model.json`
under `<suite>/model-projections/<side>/<served-protocols>/`. Each generated server receives a
`model-projection/` directory and each harness target gets `model-projections/<target-name>/`.
The manifest records exact assembled source-text hashes, model hashes, served and model-profile protocols, side, schema setting,
excluded operation/member counts, reasons, scope, and before/after definitions of every changed
shape. Protocol trait changes, route changes, and added validation errors also appear in that diff.
This is the model entering codegen; normalization is a later stage. DocumentValues is explicitly
added for JSON-only profiles, with an addition count and reason. The canonical mixed service retains
all six newly added operations, including NullableValues for XML; it does not silently inherit the
XML client declaration's omission.

A/B generation checks a protocol-neutral service-model hash against the archived baseline and the
candidate. It refuses stale or mismatched inputs. To compare a combined profile, generate its baseline
with an explicit `MP_FUZZ_MODEL_PROFILE` containing the same comma-separated protocol directories,
then use that profile for the candidate. This controls member reductions and JSON-only additions
while each generated serde server still serves one protocol. The profile must include every served protocol.
Matching a profile never authorizes changing expected behavior or suppressing a difference.

Projection tests require exactly the named operation and member to be removed and every other
canonical service operation, including operations on resources, to remain. Counts and successful generation do not establish behavior
coverage. Blocked generation records zero executed handler assertions.
Opt-in `MP_FUZZ_VERIFY_EXCLUSIONS=true` tests reproduce AWS JSON Publish.topic generation failures,
record CBOR and REST generation support, and execute empty/binary canonical REST Upload requests in both modes.
See `reports/model-projections/report.md` for observed results and remaining gaps.
The local `reports/` directory is ignored by Git; archive run evidence separately.

## What counts as a difference

`env.sh` enables semantic comparison. Every difference after the documented semantic normalization
fails. Known-regression classifiers are diagnostic only. Routing and malformed event-stream
differences are not accepted as agreement; `SMITHY_FUZZ_IGNORE_UNROUTED` and
`AFL_IGNORE_SEED_PROBLEMS` are retired and unset by env.sh.
For the semantic flag, an empty value, `0`, `false`, `no`, or `off` disables the option,
ignoring case and surrounding whitespace. Any other value enables it. `env.sh`
exports enabled flags as `1` and unsets disabled flags so the Rust driver and Python
agree. When running Python directly without `env.sh`, unset flags are disabled;
source `env.sh` to get its semantic-comparison default.

- `SMITHY_FUZZ_SEMANTIC_COMPARE`: compare the deserialized input, the status, the headers except
  `content-length`, and the body as a value (JSON member order, CBOR encoding choices and the order of
  differently-named XML siblings are ignored). Event-stream responses are decoded with CRC validation;
  frame order, typed headers, event names and exception names must match. Structured frame payloads
  are compared according to their content type; blob payloads are compared byte for byte.

A request whose handler the single-protocol server invokes must reach the same handler, with the same
input, and get the same response.

## Notes

- AFL files a difference as a hang when the driver's ten nondeterminism re-runs exceed its timeout, so
  `replay.sh` replays hangs as well.
- The seed corpus comes from `seeds.py` and modeled protocol cases. Audit the lexicon and corpus
  when operations or populated examples change.
- `fuzz.sh` regenerates and initializes by default. For manual stages, after a codegen
  change run `generate.sh` then `init.sh`; after a runtime change `init.sh` is enough.
  `FRESH=1` also discards saved crashes during initialization.
- Keep fuzzers x cases at or below the core count minus two.
- cargo-afl must match the `afl` crate in `rust-runtime/aws-smithy-fuzz/Cargo.lock` (0.15.24).
  `generate.sh` builds AFL++ under `artifacts/xdg`, so the copy in `~/.local/share/afl.rs` is not used.


## Protocol-isolated campaigns

Each A/B case pins its own protocol identity before invoking either target. The driver
replaces Content-Type with the case's media type, removes foreign smithy-protocol and
Content-Encoding headers, and removes X-Amz-Target for non-AWS-JSON cases. Header
matching is case-insensitive and duplicate variants are removed. Body bytes, operation
targets for AWS JSON, paths, methods, Accept, and other headers remain fuzzable.
AWS JSON event streams use the versioned JSON Content-Type; CBOR event streams retain
the event-stream Content-Type and pin smithy-protocol to rpc-v2-cbor.

The fixed identity is recorded as `protocol` in smithy-fuzz-config.json. Native replay
inherits it; the Python replay tool explicitly selects the case's identity too. Saved
AFL files contain raw mutations: wire headers are normalized on invocation, so raw
request dumps may show a different Content-Type from the effective request.

New campaigns use work-isolated-v1/<suite>/<case>, with separate corpus, dictionaries,
AFL output, and workers for every case. Existing work/ campaigns are preserved but
must not be copied or synchronized into these directories. Default `fuzz.sh` runs
generation and initialization before starting the campaign.

Protocol-selection and malformed/missing selection-header cases belong in dedicated
routing tests in addition to this differential comparison. The routing suppression flag is retired;
status and media-type differences between protocols fail.


### Single-protocol targets on both sides

The isolated campaign generator now sets MP_FUZZ_ISOLATE_PROTOCOLS=true. Each case
compares a generated serde single-protocol server with a schemaSerde single-protocol server.
The after server declares only that case's protocol, so an operation with no
content-type restriction cannot fall through to a different protocol. Per-protocol
after SDKs are generated under <suite>/<protocol>/schema-server. The historical
multi-protocol generator branch remains available for routing investigations, but
is not used by generate.sh. The default case list contains the five protocols;
the historical rest-xml-nojson comparison is no longer needed.
