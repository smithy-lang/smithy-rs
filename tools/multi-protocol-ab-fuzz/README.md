# A/B fuzzing: single-protocol servers versus one multi-protocol server

Sends the same fuzzed HTTP request to a legacy single-protocol server generated by `~/smithy-rs-latest`
and to a schema server generated by this checkout that serves all five protocols, and saves the request
when the two answer differently. Background: `AB_FUZZING.md` (the general runbook) and
`how-to-benchmark.md` (the same baseline/current setup, for performance).

Run the scripts with `bash` from this directory. Everything they produce goes under `artifacts/`, which
Git ignores.

```bash
bash generate.sh          # servers, harnesses, AFL++ and the driver
bash init.sh              # build both targets of every case, write seeds, compare them on the seeds
bash fuzz.sh 900 2        # 15 minutes, 2 fuzzers for each of the 12 cases
bash replay.sh            # replay saved crashes and hangs, grouped by what differs
python3 abfuzz.py cluster multiprotocol rest-json1 -v 3    # samples of each group
```

Source `env.sh` first when running `abfuzz.py` or `aws-smithy-fuzz` by hand.

## What is compared

| | Checkout | Server |
| --- | --- | --- |
| `single` | `$BASELINE_REPO` (`~/smithy-rs-latest`) | one legacy server per protocol |
| `multi` | this checkout | one `schemaSerde` server declaring every protocol |

Two suites (`SUITES`): `multiprotocol` (`multi-protocol*.smithy`) and `pokemon`, both from
`codegen-core/common-test-models` of this checkout. Six cases (`CASES`) per suite: the five protocols,
plus `rest-xml-nojson`, which compares restXml against a multi-protocol server that does not serve
restJson1. restJson1 claims REST requests without a body, so in the plain `rest-xml` case nearly every
request differs by design.

Both checkouts are used as they are, uncommitted changes included; `artifacts/gen/revisions.txt` records
their state. Nothing in the baseline checkout's source tree is modified: the generator test
(`fuzzgen/.../MultiProtocolAbFuzzHarnessTest.kt`) is compiled into its `fuzzgen` tests through
`fuzzgen-extra-tests.init.gradle`. Both fuzz targets of a case are generated by this checkout's `fuzzgen`,
so both implement the same operations; the `single` target links the baseline's runtime.

Event-stream operations are included. Handlers drain incoming events, preserve modeled error details,
and emit a deterministic example of each output event and modeled exception. Plain blob streaming
operations remain excluded.

Legacy RPC codegen rejects event-stream inputs with ordinary body members. For the shared A/B models,
`Publish.topic` and `CapturePokemon.region` are removed, and the capture route becomes
`/capture-pokemon-event`. Both targets use these same adjusted shapes on every protocol. The generated
harness integration tests separately cover initial-request frames on the schema path.

`Greet`'s `@http(code: 201)` is also dropped because a legacy awsJson server answers `201` and a schema
server `200`.

## What counts as a difference

`env.sh` enables semantic comparison. Routing exclusions are disabled by default;
set SMITHY_FUZZ_IGNORE_UNROUTED=1 only for explicit historical investigations.

- `SMITHY_FUZZ_SEMANTIC_COMPARE`: compare the deserialized input, the status, the headers except
  `content-length`, and the body as a value (JSON member order, CBOR encoding choices and the order of
  differently-named XML siblings are ignored). Event-stream responses are decoded with CRC validation;
  frame order, typed headers, event names and exception names must match. Structured frame payloads
  are compared according to their content type; blob payloads are compared byte for byte.
- `SMITHY_FUZZ_IGNORE_UNROUTED` (opt-in): accept what follows from serving several protocols. Any answer is
  accepted for a request the single-protocol server does not route (404 or 405, no handler invoked),
  and the multi-protocol server's protocol-neutral 404 is accepted when the single-protocol server also
  rejects the request, with any 4xx, before a handler runs.

A request whose handler the single-protocol server invokes must reach the same handler, with the same
input, and get the same response.

## Notes

- AFL files a difference as a hang when the driver's ten nondeterminism re-runs exceed its timeout, so
  `replay.sh` replays hangs as well.
- The models carry no `@httpRequestTests`, so the seed corpus comes from `seeds.py`. Add operations
  there when the models change.
- `init.sh` always rebuilds the targets. After a codegen change run `generate.sh` first; after a
  runtime change `init.sh` is enough. `FRESH=1 bash init.sh` also discards saved crashes.
- Keep fuzzers x cases at or below the core count minus two.
- cargo-afl must match the `afl` crate in `rust-runtime/aws-smithy-fuzz/Cargo.lock` (0.15.24).
  `generate.sh` builds AFL++ under `artifacts/xdg`, so the copy in `~/.local/share/afl.rs` is not used.


## Protocol-isolated campaigns

Each A/B case pins its own protocol identity before invoking either target. The driver
replaces Content-Type with the case's media type, removes foreign smithy-protocol and
Content-Encoding headers, and removes X-Amz-Target for non-AWS-JSON cases. Header
matching is case-insensitive and duplicate variants are removed. Body bytes, operation
targets for AWS JSON, paths, methods, Accept, and other headers remain fuzzable.
AWS JSON event streams use the versioned JSON Content-Type; CBOR event streams retain
the event-stream Content-Type and pin smithy-protocol to rpc-v2-cbor.

The fixed identity is recorded as `protocol` in smithy-fuzz-config.json. Native replay
inherits it; the Python replay tool explicitly selects the case's identity too. Saved
AFL files contain raw mutations: wire headers are normalized on invocation, so raw
request dumps may show a different Content-Type from the effective request.

New campaigns use work-isolated-v1/<suite>/<case>, with separate corpus, dictionaries,
AFL output, and workers for every case. Existing work/ campaigns are preserved but
must not be copied or synchronized into these directories. Rebuild the driver using
generate.sh and initialize fresh cases with init.sh before running fuzz.sh.

Protocol-selection and malformed/missing selection-header cases belong in dedicated
routing tests, not this differential comparison. SMITHY_FUZZ_IGNORE_UNROUTED now
defaults to disabled; do not hide status or media-type differences between protocols.
Existing explicit opt-ins remain available for investigating historical campaigns.


### Single-protocol targets on both sides

The isolated campaign generator now sets MP_FUZZ_ISOLATE_PROTOCOLS=true. Each case
compares a legacy single-protocol server with a schemaSerde single-protocol server.
The after server declares only that case's protocol, so an operation with no
content-type restriction cannot fall through to a different protocol. Per-protocol
after SDKs are generated under <suite>/<protocol>/schema-server. The historical
multi-protocol generator branch remains available for routing investigations, but
is not used by generate.sh. The default case list contains the five protocols;
the historical rest-xml-nojson comparison is no longer needed.
